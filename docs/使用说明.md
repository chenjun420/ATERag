# ATERag 使用说明

产测规格书 → 输入/输出条件 → 产测用例的抽取与评审系统。

本文档面向**部署并使用本系统的人**。仓库里只有系统本身(代码、认知词表、通用规则)与本文档;规格书、抽取结果、人工签字记录都属于**业务数据**,不入库,在你自己的环境里生成。

---

## 1. 系统做什么

给它一份产测规格书(Markdown),它输出:

1. **需求条目** —— 规格书里的功能/性能要求
2. **每条需求抽出的输入条件 / 输出条件** —— 判据从哪来、原文怎么写
3. **场景拆分** —— 一条需求按条件组合拆成多个可执行用例
4. **待人审清单** —— 规则切不出、但人读得懂的部分

下游(ATEStudio)把条件绑到用例、排测试流程、生成脚本。

**运行时永不调用 LLM。** 所有抽取是确定性的,同样的输入永远得到同样的输出。

---

## 2. 仓库里有什么,没有什么

| | 位置 | 说明 |
|---|---|---|
| ✅ **在仓库里** | `src/aterag/` | 代码 |
| | `config/*.yaml` | 认知词表:条件类型封闭词表、切分规则、章节先验、剔除词、表结构档案 |
| | `domain_rules/*/rules.yaml` | **领域通用**规则(跨型号共享) |
| | `deploy/` | 部署脚本 |
| | `docs/` | 文档 |
| ❌ **不在仓库里** | 规格书原件 | 业务输入,你自己放 |
| | `data/annotations/*.yaml` | 人工签字的兜底判据(见第 5 节) |
| | `data/registry.yaml` | 导入文档后写出的注册表 |
| | `rag_storage/` | 抽取产物、向量库侧车 |

`config/*.yaml` 与 `domain_rules/*/rules.yaml` 是**系统**:它们定义"怎么理解一份规格书",与任何具体客户无关,所以入库。

## 3. 部署

### 3.1 前置

| 组件 | 版本 | 用途 |
|---|---|---|
| Python | ≥ 3.11 | 运行时 |
| PostgreSQL | ≥ 15 | 实体存储,需 `pgvector` 扩展 |
| uv | 任意 | 依赖与虚拟环境管理 |

板卡上的完整安装脚本见 `deploy/native/`,按编号顺序执行(`01` → `07`)。

### 3.2 安装

```bash
git clone <repo-url> aterag && cd aterag

# 依赖装进项目内的虚拟环境, 不碰系统 Python
uv venv
uv pip install -e .

cp .env.example .env      # 然后填 LLM / Embedding / Postgres 等配置
```

`.env` 含密钥,**不要提交**。已在 `.gitignore` 里。

必需的环境变量:

| 变量 | 说明 |
|---|---|
| `POSTGRES_DSN` | 实体库连接串 |
| `QDRANT_URL` | 向量库地址 |
| `QDRANT_COLLECTION` | 集合名 |
| `LLM_BASE` / `LLM_MODEL` / `LLM_API_KEY` | 仅**线下**提案用;不配则提案功能不可用,抽取照常 |
| `REGISTRY_PATH` | 注册表路径(默认 `registry.yaml`) |
| `DOMAIN_RULES_DIR` | 领域规则目录(默认 `domain_rules`) |
| `ANNOTATIONS_DIR` | 人工注记目录(默认 `data/annotations`) |

> 环境变量**没有前缀**,是 `POSTGRES_DSN` 而不是 `ATERAG_POSTGRES_DSN`。

### 3.3 校验

```bash
python scripts/validate_configs.py
```

解析全部配置文件并做结构自检。缺 `config/table_schemas.yaml` 会直接报错——静默丢列比报错危险得多。

## 4. 导入规格书(业务过程)

上传文档是**业务过程的一部分**,不是部署步骤。每个客户型号走一次:

```bash
# 1. 导入并构建该型号知识库
python -m aterag.mcp_server.server     # 起 MCP 服务后用 ingest_document 工具
#    或直接调 pipeline:
python -c "
import asyncio
from aterag.ingest.pipeline import ingest_spec
..."
```

实务上通过 MCP 工具 `ingest_document` 提交文档路径。导入会:

1. 解析 Markdown、识别型号 ID(取自文档首行标题)
2. 分类章节、抽取实体入 Postgres
3. 写入 `registry.yaml`:登记该型号、记录 `doc_version`、置 `kb_status`

`registry.yaml` 是**运行时状态**。新环境里它不存在,`Registry.load` 会自动初始化为空注册表,不需要手工创建。

### 4.1 构建领域通用知识库

```bash
# MCP 工具 build_domain_kb
```

把 `domain_rules/{domain}/` 下的规则与叙述文档摄入向量库。

**这里体现一条重要约定**:`domain_rules/*/rules.yaml` 只放**领域通用**规则。规则即使是从某份规格书提炼的,也只有在评估为"该产品领域的通用规则"后才入库;不是通用规则的,应在导入该型号时自动生成进该型号的知识库,**不写进共享规则文件**。

判断标准是规则本身能否跨型号成立,而不是它的出处:

- ✅ `功率 = 电压 × 电流` —— 任何电源都成立
- ✅ `绝缘电阻 ≥ 2MΩ`(YD/T 731 国标)—— 通信电源行业通用
- ❌ `PA601 型号的告警点为 12A` —— 型号专有,不该进共享文件

`source` 字段记录规则的出处(哪份文档哪一节),但**规则匹配时不会读它**。

## 5. 人工注记:规则切不出时怎么办

### 5.1 什么时候需要

规则(短语 + 正则)能切出大部分条件,但**切不出的**会进 `unresolved_text` 队列。典型是**多层嵌套复合条件**——一句话里同时含温度、输入、负载、时间四层,正则无法完整拆开。

这时需要人读懂规格书,把语义补进去。补进来的东西叫**注记(annotation)**。

> 注记是**兜底**,不是主干。PA601 实测:95 条需求里,注记只影响 1 条,贡献 3 条条件(占 1%)。其余 94 条纯靠规则。没有注记,系统照常工作。

### 5.2 注记为什么不在仓库里

注记逐条对应某个客户型号的规格书条款,含需求编号、原文片段和签字人。入库等于把客户判据连同需求编号一起公开。

所以注记是**运行时数据**,由使用者在自己的环境里生成并签字。

### 5.3 生成一条注记

**没有工具能自动创建注记**——这是刻意的:注记是人对规格书的理解,必须由人起草。流程是"取指纹 → 手写 YAML → 评审 → 签字"。

#### 第 1 步:拿到指纹

```bash
python scripts/extract_test_conditions.py -m <MODEL_ID> --print-fingerprint SR-<MODEL_ID>-1213
```

指纹是那条需求当前内容的摘要。**注记靠它绑定文档版本**:规格书改版后指纹失配,注记自动失效并回到待审队列——不会拿旧判据套新数据。

#### 第 2 步:手写注记文件

创建 `data/annotations/<MODEL_ID>.conditions.yaml`:

```yaml
version: 1
model_id: <MODEL_ID>
entries:
  SR-<MODEL_ID>-1213:
    status: draft              # draft=未评审(语义已生效, 但置信度标 proposed)
                              # approved=已签字
    fingerprint: "<第 1 步得到的值>"
    proposed_by: <谁起草>
    approved_by: null         # --approve 时自动写入
    approved_at: null         # --approve 时自动写入
    reason: "<为什么规则切不出这一条>"
    input:
      - kind: temperature      # kind 必须在封闭词表内
        text: "<规格书原文片段>"
        value: { op: ">=", value: -25, unit: "℃" }
    output:
      - kind: timing
        text: "<规格书原文片段>"
        value: { max: 12, unit: s }
```

规则:

- `kind` 必须是 `config/condition_patterns.yaml` 里的封闭词表成员,写错会被拒
- `text` 必须是**规格书里能原文找到的片段**——`--show` 会逐条核对
- `value` 要与原文一致
- 一个需求只能有一条注记条目,输入输出都写在里面

#### 第 3 步:评审

```bash
python scripts/review_annotation.py -m <MODEL_ID> --show SR-<MODEL_ID>-1213
```

并排显示:规格书原文 → 规则推断结果 → 注记草案。`--show` 已把下列项算好,不用评审人自己比对:

- 指纹是否与当前行一致(不一致 = 规格书已改版,注记已失效)
- 每个子句的 `text` 是否能在原文里找到(防编造)
- `kind` 是否都在封闭词表内
- 注记相对规则推断是**补充**还是**改写**(改写需说明理由)

#### 第 4 步:签字

```bash
python scripts/review_annotation.py -m <MODEL_ID> --approve SR-<MODEL_ID>-1213 --by <评审人>
```

`--approve` 必须同时给 `--by`,签字要留痕。写入 `approved_by` / `approved_at`。

#### 第 5 步:确认

```bash
python scripts/review_annotation.py -m <MODEL_ID> --list     # 看状态
python scripts/review_annotation.py -m <MODEL_ID> --check    # CI 门禁: 有未评审注记则退出码 1
```

### 5.4 draft 与 approved 的区别

| status | 语义生效? | 置信度 | 能否作为产测判据 |
|---|---|---|---|
| `draft` | **是**(优于规则切分) | `proposed` | **否** |
| `approved` | 是 | 正常 | 是 |

`draft` 的条件会被标 `annotation_draft` 并计入 `stats.annotation_draft`。下游规划器**必须**把未签字条件排除在执行序列之外——未经人审的判据不能变成产测放行边界。`--check` 就是守这条的 CI 门禁。

## 6. 抽取与导出

```bash
# 抽条件
python scripts/extract_test_conditions.py -m <MODEL_ID> --brief

# 统计(条件数 / 剔除原因 / 覆盖分布)
python scripts/extract_test_conditions.py -m <MODEL_ID> --stats-only

# 导出给 ATEStudio 的 bundle
python scripts/export_studio.py -m <MODEL_ID> --out rag_storage/exports/studio_bundle.json
```

### 6.1 契约 hash

bundle 里有 `contract_hash`,是契约的指纹。**下游必须核对它**——不一致说明字段被丢了,而第一个症状是某个判据从用例里消失。

两侧独立算出同一个值,这个值被硬钉在验收脚本里。改契约会改 hash,必须两边同步。

## 7.1 交给 ATEStudio 之后

导出 bundle 之后, 评审、签字、产测流程生成都在 ATEStudio 侧, 操作手册在
ATEStudio 仓库的 `docs/操作手册-ATERag规格评审.md`。那一侧有三件事与本仓库的
产出直接相关, 值得在这里先说清:

**① 签字现在会真的改变产测序列。** 第 5 节的 `approved` 不再只是状态字段:评审签字
之后重新规划, 对应条件会从"被排除"进入执行序列(实测 `pending 62 → 60`、步数
`610 → 614`)。曾经不是这样 —— 规划直接用本仓库导出的 bundle, 而本仓库永远导出
`draft` 且没有任何东西重写那个文件, 于是签字在产测上没有作用,而 ATEStudio 侧的
提示却写着"评审签字后重新规划即可纳入"。

**② 因此"签完字要不要重新导出 bundle"的答案变了。** 不需要。ATEStudio 侧会用库里
的签字状态覆盖 bundle 上对应的条件(单向:只有 `draft` 可能变成 `approved`,且只认
`cond_fingerprint` 匹配且库中自身为 `approved` 的那一行)。所以本仓库的
`export_studio.py` 不必、也不应该在签字后重跑来"刷新"状态。

反过来,**改了 `domain_rules/` 或注记之后必须重新导出**:那会改变条件本身, 而覆盖
只动状态、不动内容。

**③ 红线的位置。** 「未批准的条件不得作为产测判据」这条规则落在 ATEStudio 的
`plan_flow`, 不在本仓库。本仓库负责把每条条件的 `status` 如实标成 `draft`;
谁都不许在导出时把它改成 `approved` —— 那是签字人的动作。

## 8. 常见问题

**导入报「无法从文档标题识别型号 ID」**
型号 ID 取自文档首行前 500 字符,须匹配 `[A-Z]{2,8}\d[A-Z0-9]*(-[A-Z0-9]+)+`。改文档标题,不要改代码。

**抽取结果里某条需求的条件明显偏少**
查 `unresolved_text` 队列——它多半在注记流程里(第 5 节)。

**注记不生效**
按顺序查:① 目录对不对(`ANNOTATIONS_DIR`,默认 `data/annotations`;注意该 env 键**无 `ATERAG_` 前缀**)② 文件名是不是 `<MODEL_ID>.conditions.yaml`③ `fingerprint` 是否与当前行一致(用 `--print-fingerprint` 重取)④ `status` 是不是 `draft` 而下游只认 `approved`。

**注记目录整个不存在**
不是错误。`AnnotationBook.load` 对缺失文件返回空书, 抽取照常跑, 只是回到纯规则
路径(PA601 实测: 95 条需求里注记只影响 1 条, 贡献 3 条条件, 占 1%; 0 条需求会
失去全部条件)。按第 5.3 节生成即可。

**`registry.yaml` 不见了**
它由 `register_product()` 运行时写出, `Registry.load` 在缺失时会自动初始化,
所以新克隆的仓库开箱即用, 不需要手工创建。

**`review_annotation.py` 报「-m 必须显式指定」**
注册了多个型号时不允许推断——批错型号的签字是静默且永久的错误。

**改了 `config/condition_patterns.yaml` 之后抽取全变了**
这是预期的:该文件定义"怎么理解一份规格书",改动等价于改变全量抽取语义。它属于系统,改动应走评审 + PR,不能由运行时顺手改掉(工作台的写入白名单刻意排除了这三个文件)。

## 9. 目录结构

```
src/aterag/
  config.py              配置
  registry.py            型号注册表 (运行时状态)
  extract/               抽取: 分词/选择/装配/场景/评估
  ingest/                摄取: 解析/分类/实体抽取
  inference/             领域推理
  rag/                   检索
  workbench/             人工评审台 (写入白名单 + 单文件 commit)
  mcp_server/            MCP 服务
config/                  认知词表 (系统)
domain_rules/            领域通用规则 (系统)
deploy/                  部署脚本
scripts/                 运维与自检脚本
tests/                   测试
data/                    运行时数据 (注记/注册表) —— 不入库
rag_storage/             抽取产物与侧车 —— 不入库
```
